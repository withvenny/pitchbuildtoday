# Pitch. Build. Today.

🌋

**Pitch. Build. Today.** is a practical blueprint for moving from raw product idea to build-ready software.

It helps founders, advisors, product teams, and AI-assisted builders convert messy notes, voice transcripts, brainstorming sessions, and early product ideas into structured artifacts that can guide planning, data modeling, API design, CMS architecture, UX design, web builds, and mobile app development.

The goal is simple:

> Reduce guesswork before code is written.

Most vibe coding fails because it asks a coding tool to interpret unclear requirements, incomplete workflows, vague data needs, undefined user roles, and half-formed product strategy. Pitch. Build. Today. gives the idea a path before it becomes code.

---

## The Core Idea

Every software product begins as intent.

Sometimes that intent is a voice memo. Sometimes it is a founder monologue. Sometimes it is a sketch, a transcript, a customer complaint, a spreadsheet, or a half-written app idea.

But deployable software needs more than intent.

It needs structure.

Pitch. Build. Today. organizes software creation into a staged blueprint:

1. Notes
2. Product Brief
3. Stories & Epics
4. Data Model
5. API
6. CMS
7. UI Mockups
8. Web App
9. Mobile App

Each stage creates a clear artifact that improves the quality of the next stage.

The rule:

> No phase should ask the next phase to guess.

---

## Why This Exists

AI-assisted coding tools are powerful, but they are not mind readers.

A vague prompt can produce a working prototype, but it usually struggles with:

- separation of concerns
- long-term maintainability
- professional handoff
- structured data modeling
- consistent API design
- admin and CMS needs
- user permissions
- workflow states
- future updates
- scalable architecture
- clear deployment paths

Pitch. Build. Today. exists to solve the gap between **having an app idea** and **having build-ready product artifacts**.

It is not a replacement for developers, designers, architects, or product managers.

It is a better front door for all of them.

## The Volcano Metaphor

The visual metaphor for Pitch. Build. Today. is a volcano.

From the top, a volcano looks like a circle.

From the side, it is an ascent.

Software works the same way.

From the user's perspective, an app may look simple: a screen, a button, a form, a result.

From the builder's perspective, that simple experience is supported by layers: product strategy, user stories, data, APIs, CMS logic, UI, deployment, and sometimes mobile binaries.

The Pitch. Build. Today. framework treats software development as a structured climb.

Each stage spirals around the same core idea at a higher level of precision.

The volcano represents:

- structured ascent
- progressive refinement
- separation of concerns
- compound clarity
- disciplined movement from idea to deployment

## The 9-Stage Build Blueprint

### 1. Notes

**Purpose:** Capture raw founder intent without forcing premature structure.

**Inputs may include:**

- voice memo transcripts
- brainstorming notes
- meeting notes
- sketches
- screenshots
- market observations
- customer complaints
- founder monologues
- rough product ideas

**Outputs may include:**

- raw notes summary
- problem inventory
- opportunity list
- assumption log
- open questions
- initial feature signals

**Quality gate:**

Can someone understand what the founder is trying to build without needing the founder to explain it again live?

---

### 2. Product Brief

**Purpose:** Turn raw intent into a coherent product vision.

**Inputs may include:**

- raw notes
- founder goals
- audience notes
- problem statements
- market context
- business model ideas

**Outputs may include:**

- product vision brief
- target user definitions
- core problem statement
- proposed offering
- value proposition
- MVP boundary
- success metrics
- business goals

**Quality gate:**

Can this product be explained to a builder, designer, advisor, or investor in under five minutes?

---

### 3. Stories & Epics

**Purpose:** Translate the product brief into user behavior and feature structure.

**Inputs may include:**

- product brief
- user roles
- use cases
- business rules
- workflow notes
- acceptance criteria

**Outputs may include:**

- epic discovery matrix
- user stories
- actor / verb / noun matrix
- acceptance criteria
- permission notes
- dependency notes
- workflow states

**Quality gate:**

Can the team identify the major jobs the application must support?

---

### 4. Data Model

**Purpose:** Convert user behavior into structured information.

**Inputs may include:**

- epics
- stories
- actor / verb / noun matrix
- workflow states
- business rules
- permissions
- reporting needs

**Outputs may include:**

- canonical data model
- entity relationship map
- data model YAML
- field dictionary
- validation rules
- enum definitions
- status lifecycle definitions
- ownership and permission mapping

**Quality gate:**

Can a database architect understand what must be stored, related, updated, protected, and queried?

---

### 5. API

**Purpose:** Define how systems and interfaces interact with the data.

**Inputs may include:**

- data model
- user stories
- workflow requirements
- authentication rules
- integration requirements
- reporting needs

**Outputs may include:**

- API resource map
- endpoint list
- OpenAPI draft
- request and response schemas
- authentication model
- authorization rules
- pagination rules
- filtering and sorting rules
- rate limits
- error states
- webhook notes

**Quality gate:**

Can a backend developer build the system contract without inventing missing product logic?

---

### 6. CMS

**Purpose:** Give operators a way to manage the product without requiring code changes.

**Inputs may include:**

- API specification
- data model
- product brief
- content requirements
- admin workflows
- role definitions
- moderation rules

**Outputs may include:**

- CMS architecture recommendation
- admin roles and permissions
- content models
- page templates
- reusable content blocks
- settings schema
- approval workflows
- content lifecycle states
- moderation requirements
- operational dashboards

**Quality gate:**

Can a non-developer manage the product after launch?

---

### 7. UI Markups

**Purpose:** Convert product logic and system behavior into visible user experience.

**Inputs may include:**

- product brief
- stories and epics
- data model
- API spec
- CMS requirements
- brand notes
- user flows

**Outputs may include:**

- UX flow map
- wireframes
- design-tool prompt
- screen-by-screen requirements
- component inventory
- form behavior notes
- loading states
- empty states
- error states
- accessibility notes

**Quality gate:**

Can a designer or frontend builder understand what every screen is supposed to do?

---

### 8. Web App

**Purpose:** Build and deploy the browser-based application experience.

**Inputs may include:**

- UI markups
- API specification
- CMS architecture
- data model
- brand system
- acceptance criteria
- deployment preferences

**Outputs may include:**

- frontend build plan
- route map
- component architecture
- state management plan
- integration plan
- environment variable list
- testing checklist
- deployment instructions
- production-ready web application

**Quality gate:**

Can users access and use the product from a browser?

---

### 9. Mobile App

**Purpose:** Extend the product into native or mobile-first environments when mobile adds real value.

**Inputs may include:**

- web app
- API specification
- mobile UX requirements
- device capability needs
- notification requirements
- offline needs

**Outputs may include:**

- mobile app brief
- mobile feature scope
- iOS build plan
- Android build plan
- push notification model
- offline behavior notes
- app store readiness checklist
- IPA / APK build package notes

**Quality gate:**

Does mobile add real product value, or is the web experience enough?

## Founder Intake Workflow

Founder Intake is the trailhead before the nine-stage ascent.

It is the structured process for capturing a founder's rough idea before turning it into product artifacts.

Founder Intake helps answer:

> What did the founder actually mean?

A founder may begin with fragments:

- “I want an app for this market.”
- “I need a dashboard.”
- “Users should upload documents.”
- “I want AI in it.”
- “It should work like Airbnb, but for my industry.”
- “I recorded a voice memo. Can this become an app?”

Founder Intake turns those fragments into usable raw material.

A strong intake process captures:

- founder intent
- target users
- core problem
- desired outcome
- product category
- user actions
- data clues
- admin needs
- integrations
- technical constraints
- MVP boundary

Founder Intake is not one of the nine official stages.

It is the trailhead.

## How To Use This Repo

### 1. Start with intake

Use the founder intake workflow to collect the raw idea, audience, problem, desired outcome, and constraints.

### 2. Convert raw notes into a product brief

Use the product brief template or agent to turn messy material into a clear product vision.

### 3. Generate stories and epics

Translate the product brief into user behaviors, workflows, permissions, and acceptance criteria.

### 4. Build the data model

Extract the entities, relationships, fields, states, and rules implied by the stories.

### 5. Design the API

Use the data model and workflows to define resource maps, endpoints, schemas, auth, and system behavior.

### 6. Define the CMS

Clarify how humans will manage content, users, settings, pages, approvals, and operational data.

### 7. Create UI mockups

Turn the product logic into user flows, screens, wireframes, and component requirements.

### 8. Build the web app

Use the artifacts to guide frontend architecture, integrations, environment configuration, testing, and deployment.

### 9. Decide whether mobile is necessary

Only build a mobile app when it adds meaningful product value.

## Design Philosophy

Pitch. Build. Today. is built on a few working beliefs:

### 1. Raw ideas are valuable, but incomplete

A messy idea is not bad. It is early.

The job is not to shame the mess.

The job is to convert it.

### 2. Requirements should compound

Each artifact should make the next artifact easier, not harder.

Product briefs should make stories easier.

Stories should make data modeling easier.

Data models should make API design easier.

APIs should make UI and CMS work easier.

### 3. Separation of concerns matters

A product brief is not a data model.

A data model is not a UI.

A UI is not an API.

A CMS is not an afterthought.

Each layer deserves its own artifact.

### 4. Vibe coding needs artifact discipline

AI coding tools are better when the handoff is better.

A better prompt helps.

A better artifact helps more.

### 5. Not every product needs every layer on day one

The blueprint is not a command to overbuild.

It is a way to think clearly about what should exist now, what can wait, and what should never be built.

## What This Is Not

Pitch. Build. Today. is not:

- a no-code platform
- a specific framework requirement
- a replacement for engineering judgment
- a promise that AI can build everything perfectly
- a rigid methodology that must be followed blindly
- a reason to build mobile before proving the web experience

It is a practical artifact system for better product planning and better software handoff.
